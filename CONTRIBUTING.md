# Contributing

This is a research codebase whose outputs are reported in a thesis. That gives
it one unusual property worth stating up front: **a silent behaviour change is
worse than a crash.** A refactor that quietly moves an accuracy number
invalidates results that have already been written up, and nothing in a normal
test suite would catch it. Most of the conventions below exist for that reason.

---

## Setup

```bash
pip install -e '.[dev]'      # tests, black, isort
cp .env.example .env         # SERPER_API_KEY or TAVILY_API_KEY at minimum
```

On the cluster, `sbatch jobs/001_setup.job` builds the `agent_engine` conda
environment instead. Note that `conda` is not on `PATH` in non-interactive
shells - invoke the interpreter by full path in scripts and job files.

## Tests

```bash
pytest -q                      # everything, from the repo root
pytest tests/unit -q
pytest tests/characterization -q
```

Run from the repo root. `pyproject.toml` pins `testpaths = ["tests"]`; without
it a bare `pytest` walks into `data/training/` directories that are readable but
not executable, and collection aborts before any test runs.

### Two kinds of test

**`tests/unit/`** - ordinary tests. Add them freely.

**`tests/characterization/`** - these lock *current* behaviour against committed
fixtures. They exist to prove a refactor changed nothing:

| Fixture | Locks |
|---|---|
| orchestrator trace | The full turn-by-turn event sequence of a run |
| metrics replay | Aggregation over frozen historical `raw_results.json` |
| failure-mode replay | `classify_failure` over the same recorded runs |

> **A failing characterization test is a finding, not a chore.** It means
> behaviour moved. Investigate before doing anything else.

Fixtures regenerate only under an explicit flag:

```bash
pytest tests/characterization -q --update-fixtures
```

Never run that to make a red test green. Run it when you have decided the new
behaviour is correct, and say so in the commit message.

The metrics and failure-mode fixtures replay *historical runs*: adding a
benchmark or a tool cannot change what an old run scored, so those two stay
valid indefinitely and are what protect the thesis numbers.

### Writing a good test here

- **Assert why, not just what.** A test expecting `False` should assert that the
  earlier conditions passed, or it will keep passing for the wrong reason after
  the code changes. This has actually happened - a mutation survived because a
  test returned `False` before ever reaching the logic under test.
- **Characterize, don't specify.** When testing existing code, record what it
  *does*. If that differs from what the docstring promises, say so in the test.
- **Never touch the network.** Stub `requests` at the module boundary and make
  the default fixture *fail* on an unstubbed call - a test that reaches the
  network hangs on a socket instead of failing fast.

## Style

- Python 3.11+, `black` (line length 100), `isort` (black profile)
- Type annotations are not required (`disallow_untyped_defs = false`)
- Match the surrounding code's naming, comment density and idiom

**Format only the files you changed.** Running `isort tests/unit/*.py` reformats
fifteen files nobody asked you to touch and buries your actual change.

**Never reformat `src/fine_tuning/agentflow/`.** It is vendored; see its
`VENDORED.md`.

## Making a change

### Adding something

There are four extension seams and a guide for each - see
[docs/guides/](docs/guides/). All four share a rule: **the orchestrator
dispatches on capability, not on name.** If your change requires an
`if tool_name == ...` in `src/agent_engine/core/`, the capability belongs in a
protocol or a spec table instead.

### Refactoring something

1. Make sure the behaviour is covered before you start. If it is not, add the
   test first - a test written after the change only proves the change is
   self-consistent.
2. Change it.
3. Run the full suite *including* characterization.
4. For anything substantial, verify against the old implementation directly:
   restore it from git under a different name and diff the outputs across many
   inputs. That catches what a handful of test cases will not.

### Finding a bug in existing code

Report it in [docs/known-issues.md](docs/known-issues.md) with a failing test
marked `xfail(strict=True)`. Then decide separately whether to fix it, because
**fixing a scoring bug changes reported numbers** - that is a research decision,
not a code cleanup, and it means re-running affected experiments.

`classify_failure` in `src/agent_engine/analysis/failure_modes.py` is **frozen**.
The thesis's taxonomy counts come from it. Add a new function rather than
changing its body.

## Configs

Most YAML under `experiments/configs/` is generated by
`scripts/generate_configs.py`. Edit the generator, not the output.

```bash
python scripts/generate_configs.py --output-root /tmp/preview   # dry run first
python scripts/generate_configs.py                              # then for real
```

Preview into a temp directory and diff before overwriting the committed tree.
The generator is **not** idempotent against hand-edited files: it will revert
them without saying so.

## Commits

- One logical change per commit; do not squash unrelated work together.
- Say **why**, not just what. The diff already shows what.
- If you regenerated a fixture, say which one and why the new behaviour is right.
- If you found a pre-existing bug, name it and link the issue entry.

Commits touching `src/` in a documentation change (say, fixing a stale path in a
comment) should mention that only comments changed, so a reviewer scanning the
log knows no behaviour moved.
