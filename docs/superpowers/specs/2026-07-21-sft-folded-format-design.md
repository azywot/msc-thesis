# SFT folded-format rebuild: design

**Date:** 2026-07-21 (revalidated 2026-08-04)
**Background:** `docs/sft_format_mismatch.md` (why SFT underperforms base).
**Validation status:** the diagnosis was re-checked on 2026-08-04 against the code and the
shipped `data/training/sft/sft_train.parquet` (968 rows) / `sft_val.parquet` (108 rows), and
it holds. 0 of 1076 rows contain `**Query Analysis:**` or `**Previous Steps:**`; 793/968
train rows are multi-turn; `_build_memory_prompt` is the only inference path (no
`history_mode` exists anywhere in the tree); `MultiTurnSFTDataset` masks loss to assistant
turns only (`multiturn_sft_dataset.py:231-236`). Every count quoted below comes from that
check. The check also surfaced two walker edge cases and one residual format gap that the
original design did not cover; they are folded in below.
**Goal:** Retrain the SFT adapter on data whose per-example shape matches what the
orchestrator feeds at inference. **The plan reuses the trajectories already generated by the
Qwen3-32B teacher and only reformats them offline into the correct (memory-folded) SFT shape;
no new collection is run.**
**Input (reuse, not regenerate):** the existing `collected_<ts>.jsonl` under
`/projects/0/gusr0608/msc-thesis/data/training/sft/`, i.e. the teacher's correct trajectories,
stored native multi-turn. Each record already carries the full `messages` list plus metadata,
which is everything needed to re-derive the folded format, so the teacher is never re-run. The
only new work is the offline reformat performed by `build_sft_parquet.py --format folded`,
followed by rerunning `007_train_sft.job` on the reformatted parquet.
**Non-goals:** re-running collection; changing GRPO or the orchestrator.
**Scope change (2026-08-04):** job `007`'s trainer settings were originally a non-goal. The
assistant-side rendering gap found during revalidation cannot be fixed from the data side, so
closing it requires touching `007` (a `data.custom_cls` pointer, plus an epoch/`save_freq`
revisit for the 3.09x row growth). Both are optional relative to the core fold; see the
fallback in that section if `007` must stay frozen.

## Invariants the implementation must preserve (verified 2026-08-04)

Three properties were checked against the raw `collected_20260605_214650.jsonl` and against
all **2995** folded rows produced from the current 968 train trajectories. All three hold
today; the tests in the Testing section lock them so the fold cannot regress them.

**1. No thinking content in SFT.** `<think>`/`</think>` occurrences in `sft_train.parquet`
and `sft_val.parquet`: **0 and 0**, with **0** orphaned closing tags. This is a real strip,
not an artefact of the teacher: **9201/9201 (100%)** of raw assistant turns contained
`<think>`, all removed by `_strip_thinking` (`build_sft_parquet.py:106-122`). Tool turns
never carried think tags (**0** occurrences), so the sub-agent side is clean too. Across all
2995 folded rows, **0** carry thinking in the loss-bearing span.

Corollary that closes the 109-row edge case above: **0** raw assistant turns nest a
`<tool_call>` inside a think block, so stripping first and then truncating at `<tool_call>`
gives byte-identical output to inference's truncate-then-strip in **all 109** cases
(**0 mismatches**). The fold may safely operate on the already-stripped content.

**2. Tool output is masked; no real tool calls.** The tool *result* is sub-agent output, not
an orchestrator decision, and must not be trained on. The tool *call* is an orchestrator
decision and **must** keep loss, otherwise the adapter learns nothing about when to call a
tool, which is the point of the run. The fold satisfies this **by construction**: results
move out of `tool`-role turns and into the folded user turn as `- Result:` prose, and VERL
masks system and user turns alike (`multiturn_sft_dataset.py:231-236`). Measured over all
2995 folded rows: **0** rows where any tool result text falls in the loss-bearing span, and
**0** rows where the loss-bearing span differs from the intended assistant target. Worked
example (answer row, 2300 tokens, 836 with loss): the tool result `y**3/2 + y` is present in
the user turn and absent from the trained span.

No tools execute during SFT. Job `007` runs plain cross-entropy over static rows with no
sub-agent vLLM server, no AgentFlow server, no rollout workers and no `SERPER_API_KEY` /
`TAVILY_API_KEY` (`007_train_sft.job:22-31`). Nothing in this change alters that.

**3. Folded format.** All 2995 rows are exactly `[system, user, assistant]`
(**0** malformed), and the loss-bearing span equals the assistant target exactly in every
row. The remaining gap is assistant-side only and is treated in its own section below.

## Problem recap

SFT rows are stored as a native multi-turn conversation
(`[system, user, assistant(plan), assistant(action), tool(result), ..., assistant(answer)]`),
but at inference the orchestrator rebuilds each turn as a single memory-folded prompt
(`[system, user(question + Query Analysis + Previous Steps)]`, `_build_memory_prompt`,
`orchestrator.py:641-664`). VERL trains loss on assistant turns only, so the adapter learns
to continue a native history it never sees at eval. Fix: convert the collected trajectories
into memory-folded **single-turn** rows offline.

## Change

Add `--format {native,folded}` to `scripts/build_sft_parquet.py`. Default `native`
(current behavior unchanged). `folded` expands each selected trajectory into single-turn
rows, one per assistant decision. Two companion flags fall out of the walker edge cases
below: `--planning-suffix` and `--drop-planning-answers`.

### Row expansion (one trajectory -> T+2 rows)

Per the decision to include the planning turn. `T+2` is the general case (plan + `T` actions
+ answer); trajectories that ended at the planning turn yield 1 row and tool-free
trajectories that planned yield 2, per the walker section. Measured over the current data the
expansion is 968 -> 2995 rows (3.09x).

1. **Planning row:** `[system, user(question + planning_suffix), assistant(plan)]`,
   reproducing `_run_planning_turn` (`orchestrator.py:721-743`).
2. **Action rows** (`k = 1..T`): `[system, user_folded(question + Query Analysis +
   Previous Steps 1..k-1), assistant(action_k)]`.
3. **Answer row:** `[system, user_folded(question + Query Analysis + all T steps),
   assistant(answer)]`.

Each emitted row is a 3-message `messages` list; VERL masks all but the single assistant
target.

### Byte-identity by construction

`user_folded` is built by `_memory_user_content`, which reproduces the exact `parts` join
of `_build_memory_prompt` and calls the orchestrator's own
`AgenticOrchestrator._format_action_history`. `action_history` entries are reconstructed
from each `(assistant, tool)` pair using the real `parse_tool_call`,
`AgenticOrchestrator._extract_sub_goal`, and `json.dumps(tool_call)` (matching
`_commit_tool_result`, `orchestrator.py:681-686`), and `result` = the tool turn's content.
These are imported from `agent_engine`, not re-implemented, so the folded prompt is
identical to what inference builds.

### Assistant-side rendering: a second, independent gap

Byte-identity above covers the system/user side only. There is a separate format gap on the
assistant side that folding alone does **not** close.

`MultiTurnSFTDataset` tokenizes each turn in isolation
(`multiturn_sft_dataset.py:183-236`), so an assistant target always renders as
`<|im_start|>assistant\n<content><|im_end|>`. Qwen3's template, rendering a conversation as a
whole, prepends an empty `<think>\n\n</think>` block to the final assistant turn, and at
inference with thinking off the generation prompt ends
`<|im_start|>assistant\n<think>\n\n</think>\n\n`. The adapter is therefore trained to begin
its output immediately after `<|im_start|>assistant\n` but sampled after an empty think block,
on **every** target.

This is measured, not inferred. VERL's own `sanity_check`
(`multiturn_sft_dataset.py:417-447`) compares per-turn concat against the whole-conversation
render and fails on **120/120** sampled rows of the current parquet, always by exactly 4
tokens (the `<think>\n\n</think>` block). Job `007` currently silences it with
`data.ignore_input_ids_mismatch=True` (`007_train_sft.job:141`).

Two remedies were tested against the Qwen3-8B tokenizer and **both fail**:

- `enable_thinking=False` (VERL's `data.enable_thinking_default`) leaves the lone-assistant
  render byte-identical. The template only emits the block when a preceding user/system turn
  exists, so rendering assistants in isolation can never produce it.
- Prepending `<think>\n\n</think>\n\n` to the target content does not survive: the template
  splits assistant content on `</think>` and discards the prefix.

**Recommended remedy: bypass `MultiTurnSFTDataset` via `data.custom_cls`.** This is a
supported extension point (`sft_trainer.py:461-466`, `load_extern_object`). Because folded
rows are single-turn by construction, the custom class is small: render
`prompt = apply_chat_template([system, user], add_generation_prompt=True, enable_thinking=False)`,
which is byte-for-byte the inference string including the think block, tokenize
`response = target + eos`, and set the loss mask to zeros over the prompt and ones over the
response. That gives exact train/inference identity on both sides and removes the need for
`ignore_input_ids_mismatch` entirely.

**Fallback if the custom class is descoped:** keep `MultiTurnSFTDataset`, accept a constant
4-token prefix difference at the start of every target, and say so explicitly in the writeup.
This is not a regression (the current native run has the same gap), but it leaves one
uncontrolled difference after a change whose entire purpose is to remove them.

### Turn classification (walker)

Classify by **position**, not by sniffing content. `_build_sft_messages`
(`collect_sft_data.py:70-91`) always emits `[system, user] + [assistant(plan)] +
output_messages`, so `messages[2]` is the planning turn whenever a plan exists. This holds
for all 968 train rows: every observed role sequence begins `system, user, assistant`, and no
row has a `tool` turn at index 3. Keep a guard anyway (if `messages[3]` is a `tool` turn the
planning turn errored and `messages[2:]` is pure `output_messages`), but do not rely on
content to find the plan.

From `messages[3:]`: an assistant turn immediately followed by a `tool` turn is an **action**
(its result is that tool turn); a trailing assistant turn not followed by a tool turn is the
**answer**.

Two `_run_planning_turn` edge cases break the original content-sniffing rule. Both are common:

- **Plan that emitted a tool call: 109 rows, 11.3%.** `orchestrator.py:757-775` stores the
  *full* generation in `raw_query_analysis`, so `messages[2]` contains a `<tool_call>`, while
  `state.query_analysis` (the value inference actually folds under `**Query Analysis:**`) is
  only `text[:idx].strip()`, where `idx` is the start of the tool call. Two consequences.
  First, the old rule "the leading assistant turn with no `<tool_call>` is the plan"
  misclassifies these rows, and they cannot pair as an action either because `messages[3]` is
  an `assistant`, not a `tool` turn, so the plan is **silently dropped** and the folded rows
  lose a `**Query Analysis:**` block that inference had. Second, even once classified
  correctly, the fold must apply the same truncation as `_run_planning_turn`; using the stored
  content verbatim leaks a `<tool_call>` block into the Query Analysis. Note the truncated
  text can still end with a stray `<sub_goal>...</sub_goal>`, which is faithful: that is
  exactly what inference folded. Verified safe to run on already-stripped content: no raw
  assistant turn nests a `<tool_call>` inside a think block, so all 109 rows truncate
  identically either way (Invariant 1).
- **Plan that emitted the final answer: 175 rows, 18.1%.** `orchestrator.py:777-783` sets
  `finished = True` at turn 0, so `output_messages` is empty and the record is exactly
  `[system, user, assistant]` with `\boxed{}` in the assistant turn (all 175 confirmed). There
  is no action and no separate answer turn. The old rule would emit a planning row whose
  target is the final answer and no answer row. Emit a single planning row for these, and
  **decide explicitly whether to keep them at all**: they teach the model to answer at turn 0,
  which is the *Premature direct answering* failure mode of the Ch 6 taxonomy, and they are
  18.1% of the training signal. Expose as `--drop-planning-answers` (default: keep, matching
  current behaviour) so the decision is recorded rather than implicit.

Tool-free trajectories that did plan (48 rows, `[system, user, assistant(plan),
assistant(answer)]`) yield planning + answer rows only.

### Hook point

Fold inside the existing per-split loop (`build_sft_parquet.py:425`), i.e. **after**
strip-thinking, strip-system-suffix, select-one-per-question, ratio-balance, and train/val
split. Folding after the split keeps all rows from one trajectory in the same split (no
question-level leakage). Each folded row carries the same `data_source / question / result /
extra_info` as its parent trajectory.

### Planning suffix

Default `_DEFAULT_PLANNING_SUFFIX_TOOLS` (tools are present; neither the collection config
nor the SFT eval config sets a custom `planning_suffix` or `gepa_prompt_path`). Exposed as
`--planning-suffix` for the case where a run used a custom one.

## Testing (TDD, runs in `cosmas-train`)

`tests/unit/test_build_sft_folded.py`:

1. 2-tool trajectory -> 4 rows (plan, action1, action2, answer); every row is
   `[system, user, assistant]` with correct roles.
2. Action row `k`'s user contains `**Previous Steps:**` with steps `1..k-1` and **not** step
   `k`; action row 1 has no `**Previous Steps:**` block.
3. Every folded user turn starts with `**Query Analysis:**` after the question; the answer
   row includes all T steps.
4. Planning row user ends with the planning suffix; its target equals the plan; targets of
   action/answer rows equal the corresponding assistant contents.
5. `--planning-suffix`/`include_planning=False` omits the planning row.
6. Tool-free trajectory -> planning + answer rows only.
7. Byte-identity guard: `_memory_user_content(q, qa, ah)` equals a reference built from the
   real `AgenticOrchestrator._format_action_history` with the same `parts` join.
8. **Plan-with-tool-call (the 109-row case):** a trajectory whose `messages[2]` contains a
   `<tool_call>` still produces a plan; the folded `**Query Analysis:**` block equals
   `content[:content.find("<tool_call>")].strip()` and contains no `<tool_call>`; the row's
   real first action is still emitted as action row 1.
9. **Planning-turn-answered (the 175-row case):** a 3-message trajectory produces exactly one
   planning row whose target is the `\boxed{}` turn, and no answer row;
   `--drop-planning-answers` drops it entirely.
10. **No silent drops:** for every fixture, the number of emitted rows equals
    `include_planning + T + has_answer`, so a misclassified turn fails loudly instead of
    vanishing.

Invariant guards (these lock the three properties above and must run over the **whole**
built parquet, not just fixtures, since they are cheap):

12. **No thinking:** no folded row contains `<think>` or `</think>` in any turn, and no
    orphaned closing tag.
13. **Tool output masked:** for every folded row, tokenise with VERL's masking rule and
    assert no tool-result substring appears in the loss-bearing span.
14. **Tool call trained:** the converse guard, so a future "mask more" change cannot silently
    kill the signal. For every action row, the loss-bearing span **does** contain the
    `<tool_call>` block.
15. **Loss span identity:** the decoded loss-bearing span equals the row's assistant target
    for every row.

If the `custom_cls` remedy is implemented, add:

11. **Train/inference identity:** the tokenized prompt the custom dataset builds for a folded
    row equals `tokenizer.apply_chat_template(orchestrator_prompt, add_generation_prompt=True,
    enable_thinking=False)` token-for-token, and the loss mask is zero over exactly that span.

## Caveats

- **Sequence length: settled, no truncation risk.** Measured by folding all 968 train rows
  and tokenising with the Qwen3-8B tokenizer: **2995 folded rows (3.09x)**, max 7301 tokens,
  p95 2044, mean 1356, against native max 7259 / p95 2344 / mean 1644. **0 rows exceed
  `data.max_length=16384`** (`007_train_sft.job:138`), so `truncation=right` never fires. The
  feared O(T^2) blowup does not materialise at these trajectory lengths.
- **Row count and epoch size:** 968 to 2995 rows and 1.59M to 4.06M total tokens (2.55x). At
  `train_batch_size=32` that is ~94 steps/epoch instead of ~30, so `trainer.total_epochs=3`
  (`007_train_sft.job:152`) becomes ~280 steps rather than ~90. Revisit epochs and
  `save_freq` so checkpoint selection still has useful granularity.
- **Empty reconstructed sub-goals:** 179 of 1234 stored action turns (14.5%) carry no
  `<sub_goal>` tag, so `_extract_sub_goal` returns `""` and the folded history shows
  `- Sub-goal:` blank. This is faithful (inference used the same extractor on the same text)
  and is not a fix bug, but it means ~15% of action targets also teach tool calls without a
  sub-goal. Worth a sentence in the writeup, not a code change.
- **`tool` role is not a distinct role to the model:** Qwen3's template renders `role: tool`
  as `<|im_start|>user\n<tool_response>...</tool_response><|im_end|>`. This does not change
  the argument (it is still a separate turn versus folded `- Result:` prose), but
  `docs/sft_format_mismatch.md` §1 describes it as a "tool-role result", which is imprecise.
- **Access:** the build input is now local (see Running). The H100 partition used by
  `007_train_sft.job` is still owned by `gusr0608`/`xchen`, so the **training run** remains
  blocked on that grant even though the build does not.
